# 0003. Выборочный CI и проверка GitHub Pages до merge

Статус: принято (2026-11-03)

## Контекст

Журналу нужны одинаковые локальные и удалённые проверки Bun/Vite, но запуск production E2E при изменении только документации создаёт лишнюю работу. При этом обязательная проверка не должна становиться неуспешной, если job пропущен по путям. Pages также нужно проверять по реальному подпути до merge, не давая PR право публикации.

## Решение

`tools/ci` выбирает jobs `test` и `web` по изменённым файлам. Документационные пути не запускают тяжёлые проверки, неизвестный путь запускает всё, а пустой список означает неизвестность и также запускает всё. Правила покрыты Vitest.

`test` выполняет TypeScript и Vitest. `web` собирает production-версию и запускает Playwright в Chromium. Один aggregate `ci` зависит от всех jobs через `if: always()` и принимает `success` или `skipped`; любой другой результат ломает gate. Защита ветки требует только `ci`.

Deploy workflow запускается для pull requests, push в `main` и вручную. Он получает `base_path` через `actions/configure-pages`, выполняет проверки и собирает `dist`. `enablement` разрешён только вне PR, job `deploy` также выполняется только вне PR. Permissions выдаются по jobs, очередь `pages` не отменяет текущий deployment.

## Альтернативы

- **Всегда запускать всё.** Проще, но дорого для изменений документации.
- **Использовать только `paths:` в workflow.** Меньше своего кода, но сложнее проверять безопасность правил.
- **Деплой только после push в `main`.** Проще, но ошибки base path обнаруживаются после merge.
- **Write permissions на весь workflow.** Меньше строк, но даёт лишние полномочия шагам и PR.

## Последствия

- (+) Одна обязательная проверка поддерживает пропущенные jobs и развитие CI.
- (+) Production-путь Pages проверяется до публикации.
- (−) Списки путей требуют поддержки при добавлении новых каталогов.
- (−) Неизвестные файлы намеренно создают дополнительную работу.
