# 0002. Процесс issue/branch/PR и защищённый `main`

Статус: принято (2026-11-03)

## Контекст

Первые изменения создавались без issues и обязательных проверок перед merge. После принятия PR ветки оставались, а GitHub разрешал merge commits и rebase merge. Проект `specialist-emulator` уже использует прослеживаемый процесс, который можно адаптировать без изменения технологий журнала.

## Решение

Работа следует последовательности:

1. каждая задача начинается с Task или Bug issue и связывается с закреплённым Roadmap #4;
2. для issue создаётся одна ветка от свежего `main` с именем `<type>/<summary>`;
3. коммиты небольшие, английские Conventional Commits, одна идея в каждом;
4. pull request заполняет шаблон, содержит `Closes #N`, английский заголовок и русское описание;
5. разрешён только squash merge после зелёного aggregate `ci`; влитые ветки удаляются автоматически.

Для `main` обязателен PR, `ci` является единственной обязательной проверкой, правила действуют на администраторов, требуются линейная история и разрешение обсуждений, force-push и удаление ветки запрещены. Пока у репозитория один maintainer, одобрения не требуются. Разрешение следовать процессу не даёт агенту неявного разрешения на merge.

## Альтернативы

- **Прямая работа в `main`.** Быстрее для одного изменения, но теряет границы проверки.
- **Договорённость без настроек GitHub.** Проще начать, но случайно нарушить процесс легче.
- **Обязательные одобрения.** Полезно команде, но самоодобрение для одного maintainer невозможно.
- **Требование актуальной ветки.** Строже, но ведёт к повторным CI для небольшого личного проекта.

## Последствия

- (+) Планы, реализация, проверки и история образуют прослеживаемый процесс.
- (+) Добавление jobs не требует изменения защиты ветки.
- (−) Даже небольшое исправление требует issue, ветку и PR.
- (−) Настройки репозитория придётся воссоздать при переносе проекта.
