# 0019. Машиночитаемая спецификация «Специалиста» в репозитории журнала

Статус: принято (2026-11-05)

## Контекст

Статья А. Волкова содержит точные технические данные компьютера «Специалист»: карту памяти, тактовые частоты, видеосигналы и тайминги развёртки. Эти же параметры нужны соседним проектам организации Specialist-PK — эмулятору `specialist-emulator` и аппаратной реализации `special20k` на FPGA. Дублирование данных в каждом репозитории ведёт к расхождениям, а извлечение их из Markdown-прозы ненадёжно. Требуется единый проверяемый источник, публикующийся вместе с сайтом.

## Решение

Параметры машины хранятся в типизированном модуле `src/content/machine.ts` как константа `specialistSpec` с интерфейсами `SpecialistSpec`, `MemoryRegion` и `VideoTiming`. Функция `validateSpec()` проверяет внутреннюю непротиворечивость: совпадение размеров и диапазонов областей, отсутствие перекрытий, полное покрытие адресного пространства 64 Кбайт и согласованность начала экранной области. Модульные тесты `machine.test.ts` фиксируют значения из статьи и проверяют отчёт об ошибках на намеренно испорченной спецификации.

Production-сборка дополнена шагом `bun scripts/export-spec.ts`: он выполняет валидацию (сборка падает при несоответствии) и записывает `dist/spec/specialist.json`. Внешние проекты получают спецификацию по стабильному URL опубликованного сайта; поле `schemaVersion` позволяет consumers обнаруживать изменения формата. Источник данных указывается в поле `source.citation`.

## Альтернативы

- **Отдельный JSON/YAML-файл без типов.** Проще для чтения, но не связан с TypeScript-кодом, ошибки в структуре обнаруживаются только потребителями.
- **Выделенный репозиторий со схемой.** Чистое разделение, но добавляет ещё один артефакт и процесс публикации ради одного файла; журнал остаётся источником текста, откуда эти данные извлечены.
- **Извлечение парсером из таблиц статьи.** Автоматически синхронно с текстом, но хрупко: формат прозы и таблиц меняется при вёрстке, а проверять корректность чисел всё равно нужно вручную.

## Последствия

- (+) Один проверяемый источник параметров для журнала, эмулятора и FPGA.
- (+) Ошибка в числах блокируется сборкой, а не обнаручивается читателями или пользователями эмулятора.
- (+) Публикация через GitHub Pages даёт публичный URL без дополнительных сервисов.
- (−) Данные существуют в двух местах внутри репозитория (проза статьи и модуль); тесты сверяют ключевые адреса и тайминги, при изменении статьи модуль нужно обновлять синхронно.
- (−) Изменение схемы требует bump `schemaVersion` и уведомления потребителей.
