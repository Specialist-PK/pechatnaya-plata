# Правила работы с репозиторием

## Основы проекта

- «Печатная плата» — статический журнал с современным editorial-дизайном, вдохновлённым техническими изданиями 1987 года.
- Тематика: микроэлектроника, домашние компьютеры, схемы, радиолюбительство и техническое творчество.
- Проект собирается Bun и Vite, использует TypeScript и собственный JSX-runtime без UI-фреймворка и виртуального DOM.
- Каждая статья хранится в `content/articles/<slug>/index.md` с YAML frontmatter, а её медиа — в `content/articles/<slug>/media/`. Vite формирует каталог метаданных, а выбранная статья лениво загружается и рендерится на клиенте.
- Целевая площадка публикации — GitHub Pages через `.github/workflows/deploy.yml`.
- Не добавлять UI-фреймворк или новую зависимость без предварительного обсуждения.

## Язык и документация

- Основной язык интерфейса, статей и документации — русский.
- Код, идентификаторы и сообщения коммитов — на английском.
- README содержит описание проекта, инструкции по локальному просмотру и публикации.
- `ROADMAP.md` отражает актуальные этапы развития проекта.
- При изменении структуры проекта, команд, процесса публикации или правил синхронно обновлять README и этот файл.

## Процесс разработки

- Работать маленькими шагами: одна идея за раз, с проверкой сборкой и тестами.
- Перед изменением архитектуры читать `docs/adr/`. Значимые решения записывать в новый ADR; принятые ADR не переписывать, а заменять новыми.
- GitHub Issues — источник планов; общий обзор находится в закреплённом [Roadmap #4](https://github.com/Specialist-PK/pechatnaya-plata/issues/4).
- Каждая задача начинается с Task или Bug issue. Для неё создаётся одна ветка от свежего `main` с именем `<type>/<summary>`. Прямые коммиты в `main` запрещены.
- Один pull request должен решать одну законченную логическую задачу и содержать `Closes #N`. Заголовок — английский Conventional Commit, описание — русское по шаблону.
- Коммиты оформлять с префиксами `feat:`, `fix:`, `docs:`, `refactor:`, `style:`, `chore:` или `ci:` и кратким описанием результата на английском.
- Merge выполняется только squash после зелёного aggregate `ci`; влитая ветка удаляется автоматически. Самостоятельный merge агентом требует отдельного явного разрешения.
- Коммиты, пуши, создание и закрытие issues и PR выполнять только с явного разрешения пользователя.
- Не хранить в репозитории секреты, временные файлы, `node_modules`, `dist`, отчёты Playwright, редакторские настройки и результаты локальной генерации.

### CI и deployment

- `tools/ci` выбирает jobs `test` и `web` по изменённым путям. При добавлении каталогов или связей между областями обновлять `tools/ci/src/select.ts` и его тесты.
- Неизвестный путь или невозможность получить diff должны запускать всё: лишняя проверка лучше пропущенной.
- Aggregate `ci` принимает `success` и `skipped`, но не failure или cancelled. Не обходить его при merge.
- `.github/workflows/deploy.yml` проверяет PR по реальному `BASE_PATH`, но не публикует Pages из PR. Job `deploy` выполняется только вне pull request.
- `actions/configure-pages` вычисляет базовый путь; не зашивать имя репозитория в workflow. Permissions выдаются по jobs, текущий deployment не отменяется.

## TypeScript, JSX и CSS

- Использовать семантическую разметку и логичную иерархию заголовков даже при динамическом создании DOM.
- Основной текст и навигация рендерятся на клиенте и требуют JavaScript; не описывать прототип как работающий без него.
- Компоненты — обычные функции, возвращающие DOM-узлы. Состояние хранится в явных переменных, изменения состояния завершаются обновлением DOM через общий метод `render`.
- Не добавлять виртуальный DOM, реактивную библиотеку или второй JSX-runtime.
- Стили размещать в глобальном CSS или CSS Modules рядом с компонентами.
- Импорты между модулями `src` вести через `@components`, `@content` и `@lib`; относительные пути оставлять только внутри одного модуля. Алиасы синхронно обновлять в `tsconfig.json` и `vite.config.ts`.
- Общие цвета, шрифты, отступы и другие параметры оформления задавать через CSS-переменные.
- Основной текст набирать системным `sans-serif` по ADR-0007. Технические обозначения, сигналы, выводы и названия микросхем выделять inline-кодом с системным жирным `monospace` по ADR-0010. Активные низким уровнем сигналы записывать как `` `/RAS` ``: renderer убирает `/` и добавляет надчёркивание. Локальные и внешние font-ресурсы не подключать.
- Сохранять современный editorial-дизайн из ADR-0004: белые страницы, тонкие границы, графитовый текст и один акцент. Не возвращать фактуру старой бумаги, потёртости, тяжёлые тени и контурные заголовки без нового решения.
- При ширине viewport от 768 px все страницы статьи образуют непрерывную вертикальную ленту по ADR-0005. Страницы имеют пропорции A4 `210:297`; при достаточной ширине показывается разворот из двух страниц без горизонтального зазора.
- Ниже 768 px статья рендерится одним непрерывным `<article>` в одну колонку по ADR-0008, без DOM-пагинации, номеров страниц в hash и навигации листания. Все текстовые блоки и иллюстрации остаются в одном длинном скролле.
- Основной текст обычных пагинированных страниц набирать в две журнальные колонки; исторические страницы могут воспроизводить специализированную сетку источника по ADR-0011. Все основные параграфы используют единый `font-size` по ADR-0012; специализированные колонки его не уменьшают, а пагинатор при необходимости добавляет страницы. Крупные иллюстрации задают страничные сетки, а параграфы дозаполняют свободные колонки по ADR-0015 без ограничений по количеству блоков; переход на новую страницу определяется только фактическим переполнением и закреплёнными позициями иллюстраций. Заставку, источник и крупные схемы размещать во всю ширину через `column-span: all`; иллюстрации с Markdown title `column` — внутри колонок. Закреплённые карта памяти и ведущая диаграмма размещаются по ADR-0017; под них резервируется место за счёт последующего переноса текста без изменения его порядка. Таблица с `caption`, совпадающим с alt-подписью изображения, визуально скрывается и связывается с ним через `aria-describedby`. Пагинация должна проверять и вертикальное, и горизонтальное переполнение.
- Markdown title поддерживает компонуемые через пробел указания `column`, `lead`, `page-end`, `spread-companion` и `embedded-caption`: колоночную иллюстрацию, ведущее изображение трёхколоночной страницы, явный конец страницы, иллюстрацию с зарезервированным местом на развороте и скрытие подписи, уже присутствующей в скане.
- Двухчастные иллюстрации размещать по ADR-0011 на соседних чётной и нечётной страницах одного разворота: одинаковые масштаб и вертикальная позиция, стык без зазора. Первая часть может делить страницу с текстом, как в оригинале. Чётная страница стоит слева; одиночные краевые страницы не порождают пустых DOM-страниц. Мобильный поток сохраняет обе части последовательно.
- Пагинация выполняется по реальным размерам DOM-блоков и пересчитывается после загрузки ресурсов и при изменении ширины. Не разрезать HTML строкой.
- В режиме страниц ручной скролл синхронизирует hash через `replaceState`; переходы стрелками клавиатуры создают запись истории и прокручивают существующую ленту. Панель навигации листания не добавлять. Не заменять DOM страниц при обычном чтении.
- Анимацию отключать при `prefers-reduced-motion`, а читаемость и доступность ставить выше имитации старой печати.

## Контент и материалы

- Публиковать законченные материалы вместо большого количества заглушек.
- Имя каталога статьи является стабильным `slug`; обязательные поля и формат описаны в README.
- Медиа указывать относительно `media/` и разрешать только через `resolveArticleMedia()`, чтобы Vite учёл владельца и `BASE_PATH`.
- Сырым HTML внутри Markdown не пользоваться: клиентский renderer его отключает.
- Отделять исторические факты от художественной стилизации и указывать источники исторических сведений.
- Сохранять стабильные hash-маршруты вида `#/article/<slug>/<page>`, чтобы ссылки переживали обновление страницы на GitHub Pages.
- **Локальное исключение из общей политики Specialist-PK:** в этом репозитории разрешается размещать любой контент, созданный с помощью ИИ, включая тексты, код, изображения, иллюстрации, аудио и видео.
- Исключение не отменяет честное обозначение синтетических материалов: не выдавать созданные ИИ тексты или изображения за подлинные исторические документы.
- Сторонние материалы по-прежнему добавлять только с подтверждённым правом использования и указанием происхождения. Исключение относится к ИИ-контенту, а не к чужим правам.
- Изображения оптимизировать; схемы и простые иллюстрации предпочтительно хранить в SVG. Очищенные сканы исторических статей хранить в WebP без уменьшения исходного разрешения; полные нетронутые страницы оригинала сохранять отдельно и связывать ссылками из источника с открытием в новой вкладке по ADR-0018.

## Проверка изменений

Обязательные команды после изменения кода или контента:

```sh
bun run typecheck
bun run test
bun run build
```

Модульные тесты располагать рядом с кодом как `*.test.ts` или `*.test.tsx`. Пользовательские сценарии Playwright размещать в `e2e/`; перед первым запуском установить Chromium через `bun run test:e2e:install` или задать `CHROME_PATH`.

Проверять production-результат в браузере, включая сборку по подпути:

```sh
BASE_PATH=/pechatnaya-plata/ bun run build
BASE_PATH=/pechatnaya-plata/ bun run preview
```

Перед завершением:

- открыть каждую изменённую статью и пройти по hash-ссылкам;
- проверить первую, последнюю и нечётную последнюю страницу разворота;
- проверить узкий мобильный и широкий экран, а также resize без дублирования страниц;
- проверить содержание, кнопки, стрелки клавиатуры, кнопки браузера «Назад» и «Вперёд»;
- убедиться в отсутствии переполнения и обрезанного текста, ошибок JavaScript и неработающих ресурсов;
- проверить заметность фокуса, альтернативные тексты и `prefers-reduced-motion`;
- после публикации дополнительно проверить сайт по адресу GitHub Pages.
